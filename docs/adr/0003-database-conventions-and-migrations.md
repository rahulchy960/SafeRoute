# ADR 0003: Database conventions and migration policy

- **Status:** Accepted
- **Date:** 2026-10-01
- **Prompt:** P003
- **Plan refs:** Plan v7 §4, §6.2, §7.1, §11, §12.2, §13.2, §15.2

## Context

- PostgreSQL + PostGIS is the only durable store (Plan v7 §4). Drizzle ORM defines the schema in
  TypeScript and generates SQL migrations; spatial queries are typed raw SQL (Plan v7 §6.2).
- The data outlives any app version: "a new app means new code against the same database, never
  a fresh empty one" (Plan v7 §15.2). Old app versions stay installed for months, and the SOS path
  must never break because of a migration (Plan v7 §13.2).
- P003 creates the first tables (`users`, `devices`, `idempotency_keys`, `audit_log`). Every later
  prompt adds tables, so the rules must be fixed now.

## Decision

### Keys and types

- Primary keys are `uuid` with `DEFAULT gen_random_uuid()` (built into PostgreSQL 13+, no extension).
  Exceptions: natural keys where the client already owns a stable id (`devices.installation_id`),
  and append-only logs (`audit_log.id bigint GENERATED ALWAYS AS IDENTITY`). **Client-generated
  UUID v7** is reserved for SOS ids (`client_sos_id`, Plan v7 §7.1), so an SOS created offline keeps
  its identity.
- Every timestamp is `timestamptz`, and sessions run in UTC. Conversion to `Asia/Kolkata` happens
  only when data is read, displayed or exported.
- `created_at` and `updated_at` (`timestamptz NOT NULL DEFAULT now()`) on mutable tables.
  `updated_at` is set by application code via Drizzle's `$onUpdate` using SQL `now()`, so it uses
  the database clock like `created_at`. There is no trigger; raw SQL updates must set it.
- Names are `snake_case` in SQL and `camelCase` properties in Drizzle. Enumerations are
  `text` + `CHECK (... in (...))` in the migration, not only in TypeScript. Positions are
  `geometry(Point, 4326)` with longitude first (see `backend/src/db/README.md`).

### Data rules

- **Soft delete only where stated:** `users.deleted_at`. Hard erasure of personal data is a job in
  P020. Other tables delete rows or cascade.
- **Store raw facts, not conclusions** (Plan v7 §15.2): categories, time bands, cells,
  moderation status and provenance are stored; scores and layers are computed at query time.
- **Personal-data columns** are marked `PERSONAL DATA` in the schema file and with a
  `COMMENT ON COLUMN` in the migration, so P020 export and erasure can find them.
- **`audit_log.metadata` and application logs never hold precise locations, tokens, phone
  numbers or message text** (Plan v7 §11, §12.2). `audit_log.actor_user_id` has no foreign key,
  so audit rows survive account deletion.
- **`idempotency_keys`** adds `response_status smallint` and `response_body jsonb` to the Plan v7 §11
  columns (key, user_id, route, response_hash, expires_at). A hash alone can detect a reused key
  with a different request but can't replay the original response, which Plan v7 §6.2 requires.
  The primary key is `(user_id, route, key)`; rows expire after 24 h (purge job in P020).

### Migrations

- Migrations are SQL files generated by `drizzle-kit generate` from `src/db/schema`, reviewed and
  committed in `backend/drizzle/`. SQL Drizzle can't express (comments, extensions) is added by
  hand before merge. **A merged migration is never edited**; a fix is a new migration.
- Forward only: there are no down migrations. Recovery is a new forward migration or a restore
  (Plan v7 §15.3).
- **Expand → deploy → migrate/backfill → contract** (Plan v7 §13.2):
  1. **Expand**: add new tables and nullable or defaulted columns; old code keeps working.
  2. **Deploy** code that writes both shapes and reads the new one.
  3. **Migrate/backfill** existing rows.
  4. **Contract**: drop old columns only once no deployed code or supported app version uses them.
- **Any destructive migration** (drop, rename, type narrowing, new NOT NULL without default) needs
  its own ADR and must not ship in a release that touches the SOS path.
- Migrations run only through `src/db/migrate.ts`: locally `pnpm db:migrate`, in production a
  Cloud Run Job (P006), **never on API startup**. The runner takes a PostgreSQL advisory lock, so
  concurrent runs serialise, and Drizzle applies all pending files in one transaction. Statements
  that can't run in a transaction (`CREATE INDEX CONCURRENTLY`) need a separate plan when they
  first appear.
- CI checks `drizzle-kit check`, that `db:generate` produces no drift, and that all migrations
  apply to a fresh PostGIS and a second run is a no-op.

## Alternatives considered

- **Prisma:** mature migrations, but PostGIS geometry and GiST indexes need raw SQL and manual
  migration edits; Plan v7 §6.2 prefers Drizzle. Rejected.
- **Hand-written SQL migrations only (e.g. node-pg-migrate):** full control, but no typed schema
  and no drift detection against TypeScript types. Rejected.
- **`drizzle-kit push` (sync schema directly):** fast locally but produces no reviewable,
  repeatable migration history. Not used, not even in development.
- **Integer / bigserial keys everywhere:** smaller, but ids become guessable and can't be created
  offline or merged across systems. Used only for append-only logs.
- **Database triggers for `updated_at`:** always correct, but hidden logic in the database; app
  code via Drizzle is enough for now. Revisit if raw-SQL updates become common (follow-up).

## Consequences

- Every schema change is reviewable SQL in a PR, with CI proving it applies cleanly and matches
  the TypeScript schema.
- Removing or renaming anything takes several releases (expand/contract) and an ADR. That's slower,
  but old app versions keep working.
- Cloud SQL must allow `CREATE EXTENSION postgis` for the migration identity (P006 follow-up).
- The API container image must ship `backend/drizzle/` next to `dist/` for the migration job (P006).
